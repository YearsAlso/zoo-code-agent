## D1 · 为什么先拆「渲染」和「输入」，而不是直接换一个 TUI 库

今天的 `_render()` 把两件事糅在一起：**决定一条事件该长什么样**与**把它写进 stdout**。
`repl()` 同样糅了两件：**读一行输入**与**驱动会话**。这带来两个具体后果：

1. 想换外观必须动 `cli.py` 的会话逻辑，反之亦然；
2. 没有 TTY 就没有输出可断言——CLI 用例只能靠 `io.StringIO` 兜住"大致如此"。

所以本变更先把**决定长什么样**抽成纯函数 `render_ops(event)`：输入是一条事件，输出是一组
`RenderOp`。渲染器只做"把 ops 写出去"这一件事，于是它可以是 plain / ansi / rich / json
里任意一个，而**行为规格与被测对象是同一份 ops**。输入侧同理：`LineSource` 是契约，
真终端用 `input()`，测试注入替身。

判据不是"代码更好看"，而是：**无 TTY、无密钥、无 `rich` 也能跑完整外壳并断言其行为**。

## D2 · 为什么不引入 prompt_toolkit / 硬依赖 rich

- 仓库的硬约定是"测试 MUST 在没有任何模型 API 密钥的环境下通过"，CI 只装 `.[dev]`。
  把渲染与输入押在必装依赖上，等于让"零依赖可跑通"这条保证变成"只要装了就能跑"。
- `readline` 是 stdlib：历史文件、行编辑、补全三件事它都能给，代价是只对 `input()` 生效——
  所以真 TTY 走 `input()`，其余走注入的流。
- `rich` 进 `tui` extra：装了更好看（diff 着色、语法高亮），没装就用自带的 ANSI 渲染器。
  **降级不是失败**，两者都 MUST 通过同一批 ops 用例。

## D3 · 中断为什么是"可继续"的

取消的既有语义（`agent-loop` 规格）：置位后在下一个边界停止，**已经派发的调用照常跑完**。
那么"打断当轮"之后要能继续，就必须让会话回到可推进的状态。这里有一个不做就一定会踩的坑：

模型已经写下"我要调用 X"，那条 `tool_use` 还在历史里。**未派发**的调用如果就这么挂着，
下一轮要么被补跑（使用者刚说了停，这不对），要么带着"无主的工具调用"发给真实提供方
（会被接口直接拒绝）。所以它必须有归宿：补一条"已取消"的工具观察并标记完成。

**已经派发**的调用是另一回事：它们照常跑完并留下自己的观察——CPython 无法安全中断线程，
既有取消语义也是这么写的。本变更不碰它们。

清 `stop_reason` / `cancel_requested` 复用 `continue_session` 的既有做法。**不重造机制**，
否则会出现"续跑安全、中断不安全"这种没人能解释的不一致。

## D4 · 横幅：为什么是几何而不是位图

`docs/assets/mark.svg` 是环 + 三条圆角横条，参数明确（圆心、半径、描边宽度、圆角半径）。
用这些参数直接算覆盖率，比"把 PNG 转成 ASCII"更清晰、可缩放、零素材、零依赖，而且**可断言**：
给定列数与配色模式，输出是确定的字符串。

配合仓库已有的两套墨色（浅底 `#223344` / 深底 `#E7EDF1`，强调色 `#33aa99` 不变），终端里的做法
更省事：**墨色用终端默认前景**（`ESC[39m`），只有中间那条强调色上真彩。于是浅底深底都自动正确，
不必探测终端背景。

降级必须显式：`cp1252` 编不出 `▀`（本仓库已经因为非 ASCII 输出在 Windows 上假失败过一次），
所以"编码不够就整块换成 ASCII"是硬要求，不是优化。

## D5 · 阶段事件为什么算本变更的活

状态行要显示"在想 / 在跑工具 / 在等审批"。阶段今天只写进会话状态——前端要么轮询 store
（与"事件流才是对外接口"的既定方向相反），要么自己从事件序列猜。加一条 `phase_changed` 事件
是**前端能用**与**前端能造**的分界；它同时也是 RPC / SDK 的前置，所以放在这里而不是留到那时。

去重是刻意的：`_set_phase` 只在阶段真的改变时发布，避免"每轮都发一条没变化的阶段"。
