## D1 · 权限映射为什么必须失败关闭

MCP 服务器报出来的工具，我们**不知道它背后做什么**。两种默认都是错的：

- 默认只读 → 一个会删数据的工具在只读策略下直接执行；
- 默认拒绝 → 使用者接了个只读的检索服务器，却每次都要放行，于是他会用 `--approve-all`，
  那才是真危险。

协议自己给了出路：`annotations.readOnlyHint`。所以规则是"**声明了才信**"：
只有服务器显式说它是只读的，才当作只读；其余一律有副作用 + 需要审批。这与权限门
（没有审批者就拒绝）、错误分类（认不出来就不重试）是同一条取舍。

`idempotentHint` 同理映射到工具声明——上一轮刚做的"重试决策依据声明"，这里正好用上。

## D2 · 为什么一行一个 JSON 而不是读 Content-Length

有些 JSON-RPC over stdio 的实现用 `Content-Length` 头（LSP 那一套）。MCP 的 stdio 传输
规定的是**一行一个 JSON 消息**。按行读实现简单，且与我们自己的测试假服务器一致；
真要兼容别的形态，那是加一个传输适配器的事，不必现在就把复杂度请进来。

## D3 · 卡住的服务器与孤儿进程

两个都必须处理，否则"接了个第三方服务器"会变成"终端偶尔卡住"或"机子里多出几个进程"：

- **每次请求带墙钟上限**：读一行时用 `select`/超时轮询，超时按失败抛出，而不是无限等；
- **会话结束关子进程**：装配层持有这些进程并在收尾时关掉；先 `terminate()`，再等一小会儿，
  还在就 `kill()`。

两者都有用例：假服务器里有一个"故意不回答"的模式，用来证明超时按失败处理而不是挂住。

## D4 · 为什么用真的子进程做测试

映射、编解码这些纯逻辑当然可以单测（也确实单测了）。但"起进程 → 握手 → 列工具 → 调用 →
关进程"这条链路的失败模式全在**边界**上：缓冲、行尾、进程退出、超时。
一个真的假服务器（几十行的 Python 脚本，只实现需要的那几个方法）能把这些一次测到，
而且不需要网络、不需要密钥。成本是一个临时文件，收益是这类问题不会留到使用者那里。
