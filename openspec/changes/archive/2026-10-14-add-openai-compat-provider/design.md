## D1 · 为什么用标准库而不是 `openai` SDK

SDK 会带来一个默认安装里没有的依赖，而本仓库的硬约定是"默认安装零密钥、可跑通、可断言"。
更重要的是：**我们真正需要的那部分很小**——一次 POST、SSE 逐行读、把 JSON 映射成契约。
`urllib.request` + `json` 足够，且没有版本漂移要跟。

代价是 SSE 解析得自己写（约二十行）。换来的是"装不装 extras 都能跑"，以及测试里可以塞一个
假传输把整条路走完——这比依赖一个 SDK 的内部行为更稳。

## D2 · 工具调用参数是 JSON **字符串**

OpenAI 协议里，助手消息的工具调用形如
`{"id": ..., "function": {"name": ..., "arguments": "{\"path\": \"a.txt\"}"}}`——
`arguments` 是**字符串**，不是对象（Anthropic 那边是对象）。写错这一处不会报错，只会表现为
**模型永远不调用任何工具**，非常难查。所以映射函数在收尾时统一 `json.loads`，
并把这个坑写进用例。

## D3 · 流式里工具调用是分片到达的

`delta.tool_calls` 的每一项可能只有 `index` 与半个 `arguments` 字符串。协议靠 `index`
把同一次调用拼起来。所以流式收尾要做的事是：按 index 累积 id / name / arguments 片段，
最后统一解析。这也是为什么"增量文本"与"最终响应"要分成两种条目交出去——
收尾必须在**看到 `[DONE]` 之后**才能算出来。

## D4 · 抽象是否真的与提供方无关（这个变更的隐藏判据）

上一轮抽了两处：流式可选能力、重试装饰器。这次新增提供方时，**循环、渲染、重试都不该改动**。
如果为了接一个新端点不得不动那三处，说明抽象的位置是错的。这是可以机械核对的一条：
本变更的 diff 里不该出现 `loop.py` / `render.py` / `retry.py`。
