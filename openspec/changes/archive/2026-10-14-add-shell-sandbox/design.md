## D1 · 探测为什么必须"真跑一次"

本机实测：`/usr/bin/sandbox-exec` 在，`which` 会命中，但套用策略直接失败
（`sandbox_apply: Operation not permitted`——因为我们自己就跑在一个沙箱里）。

如果按 `which` 判断，结果是：装配时说"沙箱已启用"，`run_shell` 把命令包装起来，
然后每条命令都以 `sandbox-exec: ...` 失败——使用者看到的是一句他无法解释的错误，
而且**所有命令都不能跑**，比没有沙箱糟得多。

所以探测是：跑一条最小的沙箱化命令（`/bin/true`），退出码为 0 才算可用。代价是装配时一次
几毫秒的子进程；收益是"启用"这两个字是真的。

## D2 · 为什么是"写限根目录 + 可选断网"，而不是更多

沙箱策略能写得非常细（哪些路径可读、哪些域名可连）。但每加一条，就多一处**看起来安全、
其实没测过**的配置。本变更要的是两件确定的事：

1. **写**只落在根目录（与临时目录）——这是 agent 最常造成的真实伤害；
2. **网络**要么通、要么不通——中间态（域名白名单）在这个规模上做不对。

读**不限制**：agent 本来就要读系统文件（看 `/etc` 下的配置、读 Python 安装目录）。
限制读会立刻让一半正常任务失败，而它拦住的"越界读凭据"这件事，权限门那一层已经在管。
这条取舍写进 README，不藏起来。

## D3 · 没有沙箱时怎么说话

`Boundary` 里带一个 `kind="none"` 与一句明确的话："边界是授权（工作目录 + 审批），不是隔离"。
横幅与 `/status` 都显示它。理由：使用者对"我批过这条命令"的心理感受，很容易等于"它被隔离了"；
把这句话摆在每场会话的开头，是纠正这个错觉最便宜的方式。

`strict` 档存在的意义也是这个：需要边界的人可以要求"没有边界就别跑"，而不是靠读文档确认。
