## D1 · 为什么不把 `stream` 塞进 `ModelClient` 协议

合并进一个协议最"干净"：只有一个契约，调用方不必判断。但代价是**所有既有实现当场失效**——
包括本仓库之外的（本项目自称"够小、能读完"，但它的模型契约是别人真会去实现的接口）。
而流式与整条返回**不是互补关系**：能流式的实现天然也能给整条，反过来不成立。

所以形状是：

- `ModelClient.complete` —— 既有契约，一个字节都不动；
- `StreamingModelClient.stream` ——**可选**的附加能力，`isinstance` 或 `getattr` 都判得出来；
- 循环优先走流式，拿不到就走整条，两条路的**产出同构**（都是 `ModelResponse`）。

判据不是"哪个更好看"，而是：**关掉流式，行为与今天逐字节一致**（`plain` 渲染的用例守住这点）。

## D2 · 增量为什么要单独一种事件，而不是把 `model_response` 拆成多次

`model_response` 的语义是"这一轮的正文与工具调用已经定下来了"，消费者（记录、预算、
脚本化断言）都依赖"收到它时正文是完整的"。把正文拆成多条 `model_response` 会让每个消费者
自己去做拼接，且同一条事件的含义随上下文变化——那是很难修的一类含糊。

所以增量是**另一条** `model_delta`，`model_response` 保持一次性、完整。同时给它加一个
`streamed` 字段：终端渲染器据此知道"正文已经边打边显示过了，别再来一遍"，
而管道与 JSON 消费者可以完全忽略这个字段，各自行为不变。

## D3 · 增量与"事件顺序 == 记录顺序"的约定

`_append_lock` 保的是"先落盘再发布，于是事件顺序与记录顺序一致"。增量在 `model_response`
落盘**之前**发布，看起来像绕过了这条约定。实际上不会：`run_turn` 只在没有在飞工具调用时才进入
`_model_turn`，所以发布增量期间**没有别的写入者**；而增量本身不产生记录——它描述的是
一条尚未定稿的正文。约定守的是"记录之间的相对顺序"，这里没有第二条记录参与。

## D4 · 假 SDK 测真路径

`AnthropicClient.stream` 要调 `self._client.messages.stream(...)`，SDK 又不在默认安装里。
做法沿用本仓库既有的那套：**把判定抽成纯函数**（`text_delta_of(event)`），
再用一个假 client 证 `stream()` 的装配（迭代事件 → 交给 `get_final_message()` → 归一化）。

这样"没装 SDK、没有网络"也能验证：增量被交出来了、收尾响应与 `complete` 同构、
SDK 的异常被包成 `ModelError`。**真实提供方的流式仍未测量**（需要密钥），这条会如实写进 README。
