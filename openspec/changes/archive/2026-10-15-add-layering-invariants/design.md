## D1 · 为什么分层表以模块为键，而不是以目录为键

目录结构是下一个变更（`restructure-engine-into-layers`）才有的东西。如果这张表写成
"`kernel/` 里的模块可以依赖 `providers/`"，那么本变更就必须先有那些目录——两件事被绑死，
其中一个坏了没法判断是哪一个。

以模块为键时，这张表在搬文件前后**语义完全不变**：搬完后只需要把键从 `model` 改成
`kernel.model`。于是"分层方向对不对"和"目录长什么样"可以被分别验证、分别回滚。

实测的层号（AST 最长路径，引擎模块 L0–L6）：

| 层 | 模块 |
|---|---|
| 0 | `agent_events` `context` `hooks` `model` `permissions` `prompting` `sandbox` `session` `skills` `version` |
| 1 | `retry` `providers` `openai_compat` `render` `commands` `tools` |
| 2 | `runtime` `mcp` `subagent` |
| 3 | `loop` |
| 4 | `agent` `dispatch` `shell` |
| 5 | `rpc` `sdk` `tui_app` |
| 6 | `tui` `cli` |

这批层号是**实测出来的**，不是设计出来的：我没有规定过"`model` 不该依赖任何东西"，
它就是不依赖。所以本变更做的是**把已经成立的事实写成可执行的断言**，而不是引入一套新规矩。

**入口与基准不在这张表里**：`main` 与 `evals` 的最长路径分别落在第 7、第 5 层，
但"能依赖任何人"比"站在第几层"更准确地描述了它们。把它们放进 `CONSUMERS` 之后，
规则反而更强了一条：**引擎模块 MUST NOT 反过来依赖它们**。

落地时补进表里的一个模块是 `tui_state`（L0）——它是 D4 拆出来的叶子。
它第一次运行时被"未登记模块"这条规则拦下了，这正是那条规则要的效果。

## D2 · 为什么用 AST + pytest，而不是 import-linter / pydeps

三个理由，按重要性排：

1. **不新增依赖**。本仓库的硬约定是"测试在没有任何模型 API 密钥的环境下通过"、
   依赖只在 `pyproject.toml` 里声明一次。为一个检查引入一个 lint 框架，与这条不对称。
2. **规则要能被读懂**。`tests/test_layout.py` 已经证明了这个模式在本仓库好用：
   不变量写在测试文件里，读者打开就能看到"我们承诺了什么"。
3. **失败信息要能定制**。要指出"哪条规则 + 哪个文件 + 哪一行"，
   通用工具给的是它自己的措辞。

代价是这段检查由我们自己维护（约 100 行）。在一个 9625 行的项目里，这是划得来的。

## D3 · 为什么不区分导入位置（函数体内的导入也算一条边）

因为实测的那个环正是这么藏起来的：`tui.run_tui` 体内 `from tui_app import FullscreenApp`，
而 `tui_app` 顶部 `from tui import ...`。只查模块顶部的检查会说"无环"——那是假的，
`tui` 与 `tui_app` 之间确实有双向依赖，只是其中一条被推迟到了调用时。

**"延迟导入"在本仓库是一个已知的手法**（`cli` → `tui`、`tui` → `tui_app`、
`tui_app` → `loop` 都用了），它的正当理由是"没装 extras 时 `import` 不该失败"。
那是可接受的动机，但它不该同时成为**隐藏依赖方向**的工具。把延迟导入算作边之后：

- "为了可选依赖而延迟"仍然成立（检查的是方向，不是位置）；
- "为了让检查通过而把 import 挪进函数"不再成立。

## D4 · 那个环怎么解：为什么是"抽出 `tui_state` 并在 `tui` 再导出"

约束来自 `add-fullscreen-tui` 已经定下的一条：**没装界面库时，任何模块的 `import` 都不该失败**，
而 `--tui` 分支要给出"请安装 extras `tui`"的可读报错，而不是一个 `ImportError` 堆栈。

这条约束排除了一个看起来最直接的方案：让 `tui.py` 在**顶部**导入 `tui_app`。
`tui_app` 模块级执行 `App, ... = _textual()`，导入它就等于要求装了 textual——
于是"不装 extras 也能 import 引擎里任何模块"这条保证立刻破掉，而无头归约的用例
（`tests/test_tui.py` 里那一批不需要界面的）也会连带失败。

另一个方向是把 `run_tui` 挪进 `tui_app`，但那会让 `cli` 的 `--tui` 分支在没装 textual 时
以 `ImportError` 收场——正是 `add-fullscreen-tui` 显式修过的那类失败。

所以取第三条：**把纯归约摘出去**。`tui_state.py` 零内部依赖，是天然的叶子；
`tui_app` 从它取状态类型，`tui` 从它再导出状态名并保留 `run_tui`。结果是
`tui → tui_app → tui_state`，环消失，而 `tui` 里那句延迟导入仍然保留
（它的动机——可选依赖——没有变）。

顺带的收益：归约是纯函数，与界面库无关，所以"界面行为"这一块永远可以在没装 textual 的环境里测。
这是 `add-fullscreen-tui` 的"状态归约 + 薄层"设计本来就想要的形状，只是当时没有目录去表达它。

## D5 · 为什么是"预算白名单"而不是一个统一上限

现状最大 824 行。如果本变更是"全部 ≤ 400 行"，它只能红着交付，或者被迫把
`split-god-modules` 提前做掉——那正是要避免的耦合（先立判据、再动结构）。

而"给存量登记今天的额度、只许下调"能**立刻生效**：从本变更落地那一刻起，
`tools.py` 只能是 823 行或更少。这条棘轮比一个暂时不达标的上限有用得多，
因为它把"正在变坏"变成了一件会红的事。

登记时实测有 **6 个**文件超 400 行（原计划以为 5 个）：除了 5 个公认的上帝模块，
还有 `openai_compat.py` 421 行。把它也登记进去比把上限抬到 450 好——
上限是设计决定，不该为了迁就一个文件而改。

实现的第二条比"只许下调"更紧：**额度 MUST 与实测相等**。这样调高额度会让检查红
（与实测不符），而 24 行余量这种"看起来在守规矩"的停摆也藏不住。

同时它给 `split-god-modules` 留了一个可断言的终点：白名单为空。

## D6 · 失败信息

三条规则各自要指出：规则名、文件（相对仓库根）、行号，以及"该模块登记在哪一层"。
修的人拿到这条信息应当不需要再读检查代码。这也是为什么检查写在测试里而不是做成工具：
措辞由我们自己定。
