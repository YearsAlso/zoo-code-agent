## D1 · 为什么"无参数进界面"要做成 TTY 门控而不是直接改默认

`python src/main.py` 无参数 = 跑调度器，是 `zfc --worker` 生成的项目约定。直接改成"永远进界面"
会有两个具体后果：管道里（`python src/main.py | head`）会试图画全屏；CI 与既有子进程用例的
行为跟着变——而它们现在是**靠"非终端"这个事实**在跑脚手架默认路径的。

门控之后：所有非终端路径**一个字节都不变**，终端里的默认行为才是新的。
这不是"看情况"，是把两件本来不同的事分开——终端里跑和管道里跑要的东西本来就不一样。

同时留 `--ui workers`：在终端里想跑调度器的场景（开发 Worker、看 tick 日志）仍然可达，
而且从"隐式默认"变成"显式选择"，反而更清楚。

**为什么判定是纯函数**：`is_tty` 与 `has_textual` 都从外部注入，于是三层决策
（终端 × 界面库 × 显式开关）的八种组合能在没有终端、没有装 Textual 的环境里逐条断言。
本项目已经为"界面行为不需要终端就能测"付过一次代价（`tui_state` 就是这么拆出来的），这里是同一招。

## D2 · 为什么美化分成"纯文本投影"与"薄层"两半

`fullscreen-tui` 规格已经把这条写成明文：界面状态由纯函数归约，界面行为 MUST 能在没有终端时断言。
所以这次的形状是：

| 东西 | 放哪 | 怎么验证 |
|---|---|---|
| 提示行文本（三种状态）、状态行文本、忙闲标记 | `tui_state.py`（纯函数） | 直接在用例里断言字符串 |
| 历史回取逻辑 | `tui_state.py`（纯函数 `History`） | 给定历史与按键，断言返回什么 |
| 边框、配色、布局、按键绑定 | `tui_app.py`（薄层） | Textual 无头驱动断言控件树 |

于是"输入区好不好用"里能变成断言的那部分**全部**有断言；剩下的是纯观感（边框圆不圆、
用什么颜色），那部分由一张**真实渲染出来的预览**给人看，而不是靠我在文字里形容。

## D3 · 输入区为什么是这个形状

键位从占位符搬到常驻提示行，理由是**时机**：占位符在按下第一个字符后立刻消失，
而"Ctrl-C 是打断当轮不是退出"这件事恰恰是敲到一半才需要知道的。原来的写法把最该常驻的信息
放在了最留不住的地方。

前缀用 `❯` 而不是 `>`：`>` 与 shell 的续行提示冲突，而 `❯` 在终端里渲染稳定、宽度明确。
**（实测）** 项目里已有 `supports_unicode()` 做降级判断（`surfaces/render/banner.py`），
但那个判断是给 logo 用的；输入前缀这一处若在不支持 unicode 的终端里退回 ASCII `>`——
这条留成 Non-goal，理由是：Textual 本身要求终端支持 unicode，装不上界面库时走的是逐行外壳。

提示行按状态分三种，而不是一行写全：等待审批时把"回车提交"列出来是**错的**——
那时回车提交不生效，列出来只会让人按了没反应。这与仓库里"不可用就不说可用"
（沙箱那条规格）是同一条取舍。

## D4 · 历史为什么值得做

它是这次唯一一件**功能**而不是观感：改动前输入框是"一次性的"，敲错一个字要整条重打。
Claude Code / Copilot CLI 的观感里，有相当一部分来自"它记得我刚才说过什么"。

逻辑极小（一个列表加一个游标），但边界不少：没有历史时按键不能有副作用、连续上翻到顶要停住、
下翻到底要**回到草稿**（不是回到最新一条）。这些边界正是把它做成纯函数、逐条断言的理由——
放在控件回调里，它们只能靠手点。

## D5 · 不做的事，以及为什么

- **不换 `TextArea` 做多行输入**：那要重做键位语义（回车是提交还是换行？Shift+Enter 在哪？），
  而这些在这个项目里没有既有判据。先把单行的形状做对。
- **不做主题系统 / 鼠标 / 分页器**：ROADMAP 的「明确不做」里已经写明，不在这里翻案。
- **不动逐行外壳**：它是另一条显示路径，这次只保证会话语义一致（既有规格已经要求）。
  真要动它，判据应当是"人和管道两种用法都还在"，那是另一个变更。
